Neural Karstogenesis

Can a model learn how limestone caves are actually shaped, and use that to generate Minecraft caves that look surveyed instead of carved by noise?

02The data

Twelve real cave systems from public LiDAR and survey sources, including USGS Valentine Cave and caves in France, Switzerland, Slovenia and Brazil. Each was rebuilt as a voxel void, aligned to its survey line and checked by eye before use.

Every split is by whole cave, and a ledger records which held-out caves have been spent. That rules out the easy win of testing on a neighbouring patch of the same cave.

    04In play

    What this work does not show
    • Only one seed, cave and placement is released, so there is no claim about realism across a population of caves.
    • The wall operator imitates a synthetic hydraulic teacher, not observed geological time.
    • Twelve caves is a small dataset, and the one completed blind review preferred the procedural baseline.
    • One release candidate failed its frozen performance gate; the final build was not re-measured.

    02What the harness had to do

    Leaving an agent alone this long works only if it can't quietly fool you, or itself. Each of these mechanisms is in the record because an unattended agent needed it.

    Write the pass rule before the result

    Each experiment was committed in three steps: a preregistration with its gate, a binding to exact inputs and hashes, then the recorded result.

    Run 533 failed its frozen performance gate on an 8.6% tail. It stayed failed, and the record calls it a negative result.

    A failure is never reclassified

    When a metric turned out to be the problem, the agent could change how the failed run is read, but not its verdict.

    Run 554 showed Run 553's feature-count metric was unstable. Run 553 is still recorded as failed.

    Blind roles catch the agent's own mistakes

    Candidates were compared with their research roles hidden, then unblinded before anything was selected.

    Run 423 picked a showcase. Run 424 unblinded it, found it was the control arm and corrected the pick.

    Audit the artifact, not the counter

    Runtime counters can pass while the saved world is wrong, so stopped saves were opened and checked cell by cell.

    Run 464 found 134 water cells inside a generated cave whose runtime counters had passed. Fixing that took until Run 531.

    Disposable worlds, failing closed

    Every experiment ran on fresh or copied worlds. The live multiplayer servers and the shared GPU were off limits.

    Run 434's first live release hit a timing bug and stopped with zero unsafe writes.

    A harness bug is not a result

    When the harness broke, the agent recorded it, changed only the broken piece and reran without looking at outcomes.

    Run 310 found a Gradle child reading the next lines of its input. Attempt B changed only stdin isolation.

    03Where I stayed in the loop

    My calls
    • Setting the question, the hard limits and what the agent could touch.
    • The blind visual review. I preferred the procedural baseline in both comparisons, and that result is published as it came out.
    • Approving release preparation. The approval is a commit of its own.
    • Deciding to stop at one exact seed and placement instead of claiming more.
    What I'd change next time
    • The blind human review came late. Earlier review would have shown sooner that realism, not engineering, was the open problem.
    • The agent found 74 failures and documented every one, but 564 runs is too many for one person to audit. The next harness needs a summary layer a reviewer can trust without reading every run.

    03What made it work

    Texturing on AMD

    Hunyuan3D's native PBR painter was widely reported as a dead end on ROCm. It came down to import order: loading torch before the custom rasterizer. The fix is written up with a proof asset.

    Rigging by type

    Creatures get a learned auto-rig. Mechanical objects get parts segmented by SAM 3, with a vision-language model reasoning about which parts hinge where.

    Resumable stages

    Each stage writes to a manifest, so a failed texture bake reruns alone.

    Limits, as recorded

    High-to-low texture baking was unfinished, scenes are only 2.5D, part segmentation depends on the input, and several model weights are non-commercial, so this stays a personal tool.

    st.04 · research · june to august 2026 · ~90 gpu-hours

    Terrain diffusion, and when to stop

    I wanted Minecraft worlds with real-looking mountains and rivers, generated by a published terrain diffusion model. Fine-tuning it worked once, spectacularly, and then taught me where the model's limits were.

    mean elevation after LoRA
    +161 m
    stats matching Earth
    10 of 12
    river exponent vs Earth
    0.21 / 0.38

    01The first win

    02Is it Earth-like?

    Against Copernicus 30 m elevation data, with the disagreement between two Earth sensors as the noise floor, the model matched Earth on 10 of 12 terrain statistics. Its river-network exponent did not: 0.21 against 0.38, lower in 17 of 17 paired windows (p = 2×10⁻⁵).

    Four base-stage LoRAs failed to fix it. In one, training loss fell from 0.875 to 0.405 while the target structure moved about 5× further from Earth: a loss going down for the wrong reason. A synthetic-data teacher (a stream-power erosion simulator producing training targets) failed calibration on all 43 settings.

    A second program trained pixel-space EDM diffusion from scratch, at 18M and 50M parameters, on 58,243 real-Earth patches. It avoided the collapse that sank the first, and SPADE conditioning doubled how strongly it followed river networks, but it missed its gates and closed itself at a registered checkpoint.

    03How both programs ended

    Closed by its own rule

    The final attempt of the first program was registered in advance with a binding clause: any failed checkpoint closes the program for good. The clause fired, and it was recorded as a closure, not a refutation, because the design itself never got tested.

    What lasts

    An internal audit had earlier found 4 of 5 headline claims defective; those were withdrawn in writing. The Appalachian hold-out region was never spent. What lasts is a drainage-realism benchmark I couldn't find in published work.

    02Characters from synthetic conversations

    I wanted three AI characters whose personalities shape how they reason, not only how they talk. There was no data for characters that don't exist, so I built a pipeline to make it.

    1. Biblepersona, history, opinions
    2. GenerateClaude writes data
    3. Filterformat, length, voice
    4. Mixchat, logs, multi-turn
    5. LoRAUnsloth, rank 64
    6. Comparebase vs tuned
    • Character bibles first. Each character has a written personality, a history of 16,000 to 26,000 characters, opinions and relationships, and a shared lore file. A domain list spreads the conversations across more than 15 kinds of talk, from casual chat to negotiation.
    • Four data types. Conversations with in-character reasoning, internal journal entries with no user at all, 10 to 20 turn conversations where the character steers or refuses, and chosen-versus-flat preference pairs.
    • Automatic quality filter. Every item is checked for format, length, a reasoning block, forbidden phrases and a voice score against each character's marker words before it reaches training.
    • Two rounds. v1 (about 200 examples per character) showed speech patterns transfer. v2 (about 350) went after reasoning and agency. Qwen3.5-9B first, then Gemma 4 E4B, both trained on the 128 GB AMD box under ROCm.

    job · denali · 2025–2026

    Summit, the harness Claude works in

    My team's model factory: bring in images, label them, have a person accept the labels, freeze the data, train, register, score, and write down what was learned. People use it in a browser. Claude uses the same functions through about 147 MCP tools.

    01The loop

    1. Imagesbring in
    2. LabelVLM or SAM 3 first pass
    3. Accepta person only
    4. Snapshotfrozen data
    5. Trainthrough Summit
    6. Registerlineage, card, sha256
    7. Scoreeval service
    8. Verdictnumber + decision

    A capable agent with GPU access can train many models quickly. Without a harness, that produces runs nobody can explain, labels nobody checked, and wins nobody can reproduce. The rules sit in the server, not only in the prompt, so they hold whichever Claude session, script or person is calling.

    02The rules, in the server

    Every run states its bet

    A training run carries a hypothesis and a change class. When the score comes back, a verdict closes the bet with the number and a decision.

    Claude can't confirm its own result

    A result Claude reports itself is only “claimed”. It becomes “confirmed” only when Summit re-reads the metric from a real run or eval.

    People own the ground truth

    Claude can label thousands of images but cannot accept them. The server refuses, and saves the request as a suggestion for a person. Training refuses data still pending review.

    Everything is reproducible

    Runs and evals point at frozen snapshots, and every model has a lineage node, a card and a sha256.

    Dangerous actions need the person

    Destructive tools need the person's intent in the current session. Unattended agents get a token that cannot delete anything.

    People see everything

    The lineage tree, model cards, the review queue and the hypothesis-to-verdict trail show what Claude did and what is waiting on a person.

    03Evidence the guardrails work

    In an ablation of the team plugin that carries these rules to every Claude Code session, 53 cases under 5 conditions gave 371 runs. Harmful agent runs fell from 4 of 82 with hand-wired tools to 0 of 82 with the plugin, and task outcome rose from 0.73 to 0.93.
